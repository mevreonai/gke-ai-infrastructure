Profiler: real data, wrong semantic interpretation
This is an important nuance.
The dashboard's:
46.0% NCCL in prefill 
86.3% NCCL in decode 
are real numbers.
But they are from single-node TP4 Nsight:
profiles_single_node/tp4_prefill/cuda_gpu_kern_sum.csv
and
profiles_single_node/tp4_decode/cuda_gpu_kern_sum.csv.
They represent:
share of aggregate GPU kernel time, not request wall-clock critical path.
The raw PROFILE_ANALYSIS.json explicitly warns:
aggregate GPU kernel work is NOT wall-clock critical-path time.
So the existing “Where did the time go?” ledger is too strong.
For example:
54% GPU compute + 46% NCCL = full prefill critical path
is not justified.
Similarly:
residual = 0%
is not defensible.
A better title would be:
“TP4/PP1 Aggregate GPU Kernel-Time Composition”
Then the values are legitimate.
For true critical-path attribution, you need a timeline-aware join that accounts for:
parallel streams 
overlap 
multiple GPUs 
NCCL concurrency 
host gaps 
pipeline boundaries

The V7 concept we discussed remains right, but the data layer needs one stricter rule:
No manually maintained numerical Chart.js arrays.
Every chart should be generated from a normalized data object produced from:
FINAL_VALIDATION.json 
coverage.json 
combined_vllm_runs.json 
hardware_processed/summary.json 
NCCL_POLICY_AUDIT.json
