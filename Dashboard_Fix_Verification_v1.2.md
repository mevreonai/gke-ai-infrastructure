## 7. Profiler tab — one unified "where the time goes" bar chart

**Yes, and it already exists; it only needs to move — and it now comes in two pairs.** The §4.17 wall-time budget the build added to the Long Context & 1M tab (as two tables, with "Wall-Time Budget" tiles on the Executive, Long Context and Profiler hero rows) is exactly the unified break-up: for the first token — queue (admission wait) · prefill collectives (AllReduce) · pipeline waits (SendRecv) · prefill kernels (attention, GEMM, MoE) · steps shared with other requests (their decode tokens, their prefill chunks) · time outside the engine (tokenise, transfer, API server, schedule, sample); for every token after it — collectives · pipeline hops · memory-speed floor · kernels above the floor · waiting behind other requests' prefill chunks. Rendered as 100 %-stacked horizontal bars, one row per operating point, total at the right, † on modelled rows, they read in one glance; the tables do not. The four charts are in the companion note (`PIP_Magnifying_Glass_v1.2`, pages E2E·A–D) and are delivered next to this file as PNGs plus the row data as CSV, so the team can either embed the images or feed the CSV to the dashboard's own chart library (`time_budget/README_time_budget.md` holds the column definitions):

* `time_budget/wall_time_budget_first_token.png` + `.csv` — six layouts at 128K / 512K / 1M, TP4 and TP8 at 8K, four loaded TP4/PP1 points (24 rows): queue_s, prefill_collectives_s, pipeline_waits_s, prefill_kernels_s, shared_steps_s, outside_engine_s (sums to the measured first-token time).
* `time_budget/wall_time_budget_decode_token.png` + `.csv` — the same 24 rows: collectives_ms, pipeline_hops_ms, memory_floor_ms, kernels_above_floor_ms, waiting_behind_prefills_ms (sums to the measured inter-token time).
* `time_budget/wall_time_budget_first_token_under_load.png` + `.csv` and `time_budget/wall_time_budget_decode_token_under_load.png` + `.csv` — **every loaded point the pilot ran** (24 rows each): TP4/PP1 at 8K (c1, c4, c8, c16, c32, open loop 0.75× and 1.0×), 128K (c1, c4, c8, c16, open loop 0.50× and 1.0×), 512K (c1, c2, c4), 1M (c1, c2, c4), and TP8/PP1 at 8K (c1, c8) and 1M (c1, c2, c4); the c1 row anchors each group. **Why the first pair shows only four loaded rows, and why the distributed layouts have none.** The four were a deliberate trim so the six-layout comparison stayed readable; the under-load pair now carries the full set. The distributed layouts (TP4/PP2, TP8/PP2, TP4/PP4, TP16/PP1) were run at one request only (§6 table), so they have no loaded rows anywhere — that is the open run on the list, not a presentation choice; the under-load charts should say so in their caption.

**How the loaded rows are split (so the dashboard caption can say it in one line).** First token: queue and prefill are the engine's histograms, and they are exact — the engine's decode time equals the client's (e2e − first token) within 0.4 % on every loaded run, so the residual outside queue + prefill is real time outside the engine core; the request's own prefill is the single request's of the same case family and everything above it is "steps shared with other requests"; the collective-vs-kernel split inside the prefill is the single request's (a chunk does the same work under load). Decode token: the own step is the median *normal* token (ITL ≤ 100 ms, the stall threshold the build already uses), waiting is mean − own, and the number of requests decoding when a normal token was produced comes from the client traces; the memory floor at that batch counts the 1.6 B parameters every step reads plus the expert weights a batch of that many tokens is expected to touch (8 of 256 per token, uniform routing — an upper estimate) plus the decoders' KV, at the measured copy bandwidth; the collective is the measured single-request collective scaled along the α-β curve to the batch's message size.

**Two findings the loaded rows surface — worth a sentence each on the Profiler and Scheduler tabs:**

1. *The 8K first token doubles at c4 for a nameable reason.* The own prefill goes 0.21 → 0.42 s (2.0×) while the queue is 27 ms: the 8,192-token prompt equals `max_num_batched_tokens`, so as soon as one decode token sits in the step the prompt needs a second chunk, and that tail chunk waits a full step behind the next prompt's first chunk. The per-request trace shows it directly — a wave's first tokens land at 0.23, 0.65, 0.87, 0.88 s, one chunk-step apart with a double step for the second request. A five-minute check settles it (8K c4 with the budget at 8,448, or prompts of 8,000 tokens): if the own prefill falls back to about 0.21 s it is a one-flag fix worth 211 ms of first token at c4. The Scheduler tab's chunk-size panel is the natural place for the note.
2. *Batching an MoE decode pulls in more experts.* The own step grows 4.5 → 15.8 ms from c1 to c32 at 8K and 22.9 ms at full load, and the memory floor explains most of it: a batch of 32 tokens is expected to touch 163 of 256 experts and a batch of 64 touches 222, so the weights read per step rise from 0.9 ms to 10.5 and 14.9 ms at memory speed while the kernels above the floor stay at 2.5–4.8 ms. By c16 the step is memory-bound again — on weights rather than on KV — which is why tokens per second grow sub-linearly with concurrency on this model and where the usable-throughput knee comes from. The uniform-routing expert count is an upper estimate; an expert-hit histogram from the router (one counter) would replace it, and a graphs-on torch capture at c8 and c32 (ten minutes) would split the kernels. Under load the time outside the engine also grows (15 → 232 ms per request at 8K, 0.19 → 1.0 s at 128K c16): API-server time, tokenising and admitting simultaneous arrivals one after another — the one term no engine counter splits.

For the long-prompt rows the loaded charts say in pictures what D1 and D2 say in numbers: the queue is 84 % of the first token at 128K c16 and 58 % at 1M c4; waiting behind other prefills is 95 % of a 128K c16 token and 96 % of a 1M c4 token; at 512K and 1M exactly one request decodes at a time, so the own step is the single-request token to the digit.

This is an addition only: the kernel-composition card, the torch graphs-on panel and the eager-mode captures stay exactly as they are, with their captions; the Long Context tab keeps the §4.17 tables; the Executive keeps its tile. Nothing on the Profiler tab or elsewhere is replaced or deleted by this change. If only one place is possible, Profiler. Two things to say in the caption so the charts are not over-read: the totals are measured on every row (client first-token / inter-token time, engine queue and prefill histograms), and the *splits* are measured where a per-rank capture or the graphs-on torch budget exists and modelled from measured per-call costs elsewhere (†). And one thing the archive cannot split yet: "scheduling" as such. The engine's histograms give queue, prefill and decode per request; what is left after them — tokenising, transferring the prompt, the API server, the scheduler's bookkeeping, sampling the first token — is one remainder (1–7 % of a single request's first token, 14 ms at 8K and 1.4 s at 1M; 14–27 % under load at 8K). Splitting scheduling out of that needs per-request phase timestamps kept per request instead of aggregated into histograms (the same counters, no new run), which is the first item in the panel's "what would sharpen it" list.

**On "waves".** Two different things carry that name and neither is a missing category here. (1) In vLLM's V1 engine, a *wave* is a data-parallel coordination device: when DP > 1 (and with expert parallelism, where every MoE layer needs every rank in the all-to-all), the engine cores step in lockstep, idle ranks run dummy forward passes so the collectives complete, and `current_wave` counts the episodes of activity so new requests join the next wave. This campaign ran DP = 1, EP = 1 (stated on the Evidence tab), so no waves existed and no time was spent in lockstep or dummy steps; if DP/EP layouts are added, the budget gains a new segment ("lockstep / dummy-step wait") that the engine's step timings would expose. (2) In GPU kernel terms, a *wave* is one pass of a kernel's thread blocks over the SMs; a grid whose last wave fills the SMs only partly wastes the rest of that wave — "wave quantization", the tail effect that makes small-batch GEMV and MoE kernels run at 43 % of memory speed at one request. That is real on this box, but it lives *inside* the "kernels above the memory floor" segment, not beside it; attributing it per kernel needs occupancy counters (NCU, the plan's L6 "targeted" layer), not the serving data we have. So the chart's categories are the right top level — queue, collectives, pipeline waits, kernels (with the memory floor marked), sharing / waiting on other requests, overhead — and "waves" is a sub-split of one of them that a later targeted capture can add.
