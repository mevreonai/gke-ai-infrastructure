**What this note answers.** The team's "what failed in V8 / what to re-run" analysis, row by row and proposal by proposal, followed by the gaps that analysis does not mention and a re-run plan ordered by what each run can change in the published numbers per hour of machine time.

## 0. Verdict in one paragraph

Of the five "failed or missing" rows, two are right (50G/10G serving was never run; the NCCL audit flag is a false alarm), one is half right (the PP4 stage imbalance is structural, but the stage that is heavy and the size of the bubble are both wrong), and two are wrong in ways that would mislead if forwarded: decode profiling did not fail — the decode budget is measured graphs-on and closes on the serving token within 1%, what failed is the multi-node Nsight *export*; and the "0.12% FP8 difference inside the noise floor" cannot exist, because no FP8 KV run ever produced a result. The variance row is also overstated: the archive already contains 2–4 effective repeats of ten operating points and they put the single-request noise floor at ≤ 0.6% and the long-prompt loaded floor at ≤ 0.5%. Of the five proposed re-runs, two are right as stated (graphs-on decode capture; targeted repeats), one is right with two corrections (DP = 2 × TP8, with EP kept inside a node and run under load), one should be redirected (NUMA pinning — the stall it targets was never measured; what pinning can test is the API server under load and the host side of TP8's extra collective cost), and one is premature (long-context accuracy for an FP8 KV cache that does not yet run on this stack). The list misses the cheapest, highest-leverage runs: the 8K chunk-budget check (5 minutes, could change every loaded 8K first-token number), the distributed layouts under load (the largest coverage hole in V8), the PP2 15/12 split, the 8-GPU KV-pool question, and prompts shorter than 8K, which were never run — plus one analysis fix that needs no run: closed-loop means include a start burst that never recurs (at 8K c32 the first wave averages 3.7 s to first token, the 96 requests after it 0.94 s).

## 3. What the list misses

Ranked by what the run can change in the published numbers per hour of machine time.

1. **The 8K prompt equals the chunk budget (5–10 min).** Every 8K run uses 8,192-token prompts with `max_num_batched_tokens 8192`. At one request that is one chunk; under load, one decode token in the step forces a second chunk, and that tail chunk waits a full step behind the next prompt's first chunk. The engine's prefill phase doubles (0.207 → 0.418 s at c4 while the queue is 27 ms), and the per-request trace shows it directly (one wave's first tokens: 0.23, 0.65, 0.87, 0.88 s). Re-run 8K c4 and c32 with the budget at 8,448 (or 8,000-token prompts): if the prefill falls back to ~0.21 s, every loaded 8K first-token number in V8 carries a one-flag artefact and the open-loop 8K first tokens should be re-stated. The decode and usable-throughput numbers are unaffected (they rest on p95 TPOT).
2. **Distributed layouts under load (~3 h).** TP4/PP2, TP8/PP2, TP4/PP4 and TP16/PP1 were run at one request only. Every concurrency, stall, admission and Long-Context c2–c4 panel is single-node, and the dashboard still reads as if it generalised. Run TP4/PP4 and TP16 at 128K c2 / c4 / c8 and 1M c2 / c4 (plus 8K c8), native fabric; add TP4/PP2 if time allows. This is the one run that feeds the most panels.
3. **PP2 15/12 layer split (20 min).** The cost model predicts stage-0 idle 10.1 → 3.2% and first token −3.5% on TP4/PP2 and TP8/PP2 at 128K and 512K; it is the independent test of the model and the cheapest latency win in the plan.
4. **The 8-GPU KV pool question (0 min).** D3: the TP8 pool should be ~19% larger than TP4's (same replicated latent per token, half the weights per GPU) and is 1% larger (8.21 vs 8.14 M tokens). The engine logs the KV block count at start-up; one read of the TP4 and TP8 logs says whether memory is being reserved elsewhere.
5. **Prompts shorter than 8K (30 min).** The shortest prompt in V8 is 8,192 tokens, so the interactive short-prompt regime — where the AllReduce share is highest and the chunk artefact above does not apply — is untested. TP4 at 1K and 2K: c1, c8, c32 and one open-loop sweep.
6. **Re-capture the TP16 512K prefill (15 min).** 1 of 12 ranks usable; the TP16 512K and 1M splits on the wall-time pages are modelled from that one rank.
7. **NCCL plugin and socket threads (15 min).** Already in the brief's §3c (A3) but missing from the team's list: across nodes NCCL ran on plain TCP sockets with the provider plugin off and default socket threads, and moved 57 Gb/s of a 174 Gb/s link. The 227–290 µs small-message cost and TP16's penalty both sit on that configuration; fifteen minutes of nccl-tests with the plugin and more socket threads says how much of it is configuration rather than fabric — the direct test of the "comm is not the hardware bottleneck" argument.
8. **Closed-loop edges (0 min to re-report; a rule for every new run).** A closed-loop run sends its first N requests together — a burst that never recurs — and its last wave decodes with nobody arriving behind it. With four waves per 8K point the burst dominates the mean first token: at 8K c32 the first 32 requests average 3.7 s, the 96 after them 0.94 s, against a run mean of 1.62 s (c16: 2.0 vs 0.88 s; c8: 1.1 vs 0.81 s; 128K c8: 20.3 vs 8.8 s). The drain does the opposite to the token: 8K c32 runs at 34.5 ms per token over the whole run and 37.0 ms without its last wave; 128K c8 at 188 vs 218 ms. Open-loop runs have no synchronised start and show no ramp. Re-report the closed-loop points with the first wave trimmed for first token and the last wave trimmed for the token (per-request logs are kept, so this is analysis, not a run), and size every new closed-loop point at ten waves or more. The brief is unaffected: its loaded numbers are open loop, and its concurrency points at 512K and 1M are one wave by design (D1).
