## 1. Configuration Selection Workflow

The suite is **configuration-driven**: you select the target hardware configuration, model, network bandwidth, and test stages, and the runner scripts dynamically filter out unselected tests and execute **only** your selected configuration.

### 1.1 Configuring via `RUN_CONFIG.env`

Open [`RUN_CONFIG.env`](file:///c:/Users/ayu23/OneDrive/Desktop/tpu/Performance_Intelligence_Platform/scripts/RUN_CONFIG.env) and modify the selection variables:

```bash
# ------------------------------------------------------------------------------
# 1. Cluster Hardware & IPs
# ------------------------------------------------------------------------------
export NODE0_IP="10.128.0.43"
export NODE1_IP="10.128.0.44"

# ------------------------------------------------------------------------------
# 2. Model Selection (Model-Agnostic: Point to any HuggingFace ID or local path)
# ------------------------------------------------------------------------------
export MODEL="moonshotai/Kimi-Linear-48B-A3B-Instruct"
export REVISION="e1df551a447157d4658b573f9a695d57658590e9"

# ------------------------------------------------------------------------------
# 3. Topology Filter: Choose one, multiple, or 'all'
# Options: all | tp4_pp1 | tp8_pp1 | tp4_pp2 | tp8_pp2 | tp4_pp4 | tp16_pp1
# ------------------------------------------------------------------------------
export TOPOLOGY_SELECTION="tp4_pp1,tp4_pp2"

# ------------------------------------------------------------------------------
# 4. Network Bandwidth Modes: Choose one, multiple, or 'all'
# Options: all | native | 100g | 20g | impaired
# ------------------------------------------------------------------------------
export NETWORK_BANDWIDTH_SELECTION="native,100g"

# ------------------------------------------------------------------------------
# 5. Characterization Stages: Choose one or 'all'
# Options:
#   1   -> Stage 1: Quick Wins & Single-Node (Steps 1-7: ~1h 10m)
#   2   -> Stage 2: Scale-Out Concurrency & Asymmetric PP (Steps 8-13: ~3h 30m)
#   3   -> Stage 3: Deep Profiling & Strategic Sweeps (Steps 14-15: ~2h 30m)
#   all -> All stages (Steps 0-17: ~7h 10m)
# ------------------------------------------------------------------------------
export STAGE_SELECTION="1"

# ------------------------------------------------------------------------------
# 6. Continuous Batching Sweep Blocks: Choose blocks (1 to 7) or 'all'
# Options: all | 1 | 2 | 3 | 4 | 5 | 6 | 7 | comma-separated list (e.g. 1,2,4)
# ------------------------------------------------------------------------------
export CB_BLOCKS="1,2"
```

Once saved, simply run:
```bash
bash run_master_benchmark.sh
```
The script loads `RUN_CONFIG.env` and automatically filters the benchmark matrix.

---

### 1.2 Configuring via CLI Arguments

Every configuration can also be overridden directly on the command line without editing files:

```bash
# Run only TP4 single-node and dual-node topologies on Stage 1
bash run_master_benchmark.sh --topologies tp4_pp1,tp4_pp2 --stage 1

# Run with a custom model and specific network bandwidth
bash run_master_benchmark.sh --model meta-llama/Llama-3.1-70B-Instruct --bandwidth native

# Run only a specific step (e.g. Step 4: NUMA pinning)
bash run_master_benchmark.sh --step 4

# Run only Continuous Batching Blocks 1 and 2
bash run_master_benchmark.sh --continuous-batching --cb-blocks 1,2

# Fast verification of commands and configs without launching GPU workloads
bash run_master_benchmark.sh --dry-run
```

### 1.3 Selection Matrix Reference

| Selection Parameter | Valid Values | What Gets Executed |
|---------------------|--------------|-------------------|
| `TOPOLOGY_SELECTION` | `tp4_pp1` | Single-node 4-GPU tensor parallel |

| | `2` | Step budget sweep (4K, 8K, 16K, 32K on TP4/PP1 and TP4/PP2) |
| | `3` | Request cap binding (`max-num-seqs` 16, 32, 64) |
| | `4` | Mixed traffic concurrent streams (short 1K + long 128K) |
| | `5` | Memory pressure under load (KV cache limit 4GB vs 8GB vs unconstrained) |
| | `6` | Long answers (1024, 2048 decode steps) |
| | `7` | Steady arrivals (Poisson vs fixed-rate on two servers) |

## 3. Telemetry, Waves, Stalls & Profiling Tool Scripts

### `pip_waves.py`
- **Location:** [`Performance_Intelligence_Platform/scripts/pip_waves.py`](file:///c:/Users/ayu23/OneDrive/Desktop/tpu/Performance_Intelligence_Platform/scripts/pip_waves.py)
- **Role:** Analyzes detailed request timings from a `vllm bench serve --save-detailed` result JSON. Determines who waited for whom, reconstructs arrival waves, computes first-wave spacing, detects stalls (token gaps > 100ms), and identifies engine decode silences (pauses).
- **Usage:**
  ```bash
  python3 pip_waves.py <run.json> [--budget 8192] [--json out.json]
  ```
- **Exact Results & Outputs:**
  - **Console Output / JSON File:**
    - `n`: Total request count
    - `C`: Concurrency
    - `lone_read_s`: Duration of the first prompt prefill without contention (lone read $R$)
    - `first_wave_reads`: Array of normalized waiting times for the first wave
    - `step_reads`: Spacing of requests within the first wave (1.0 = one at a time, 0.5 = two side-by-side)
    - `burst_share_of_waiting`: Percentage of total run waiting time spent in the opening burst
    - `stalls`: Count and duration of token gaps > 100ms where decode was blocked by prefill
    - `pause`: Detection of decode silences $\ge 3$ normal steps (pink band pause)

### `pip_step_cost.py`
- **Location:** [`Performance_Intelligence_Platform/scripts/pip_step_cost.py`](file:///c:/Users/ayu23/OneDrive/Desktop/tpu/Performance_Intelligence_Platform/scripts/pip_step_cost.py)
- **Role:** Parses vLLM engine iteration lines in `server.log` and fits the continuous batching step-cost linear model:
  $$\text{Time (ms)} \approx a + b \cdot (\text{generation\_requests}) + c \cdot (\text{context\_tokens})$$
- **Usage:**
  ```bash
  python3 pip_step_cost.py <server.log> [--json step_cost.json]
  ```
- **Exact Results & Outputs:**
  - **JSON Output (`step_cost.json`):**
    - `base_overhead_a_ms`: Fixed scheduling overhead per step ($a$)
    - `marginal_decode_b_ms`: Incremental cost per active token generation ($b$)
    - `marginal_prefill_c_ms`: Incremental cost per prompt chunk token ($c$)
    - `r_squared`: Goodness of fit ($R^2$, typically > 0.95)
    - `rmse_ms`: Root mean squared error in milliseconds
    - `sample_count`: Number of iterations parsed

## 5. Master Results & Artifact Output Inventory

When you run any script in the Performance Intelligence Platform, here is the complete inventory of exact files and metrics produced:

### 1. Benchmark Metrics (`<bench_name>.json`)
Every benchmark execution generates a JSON file with:
- **Throughput:**
  - `request_throughput`: Completed requests per second (req/s)
  - `output_throughput`: Generated tokens per second (tok/s)
  - `total_token_throughput`: Combined input + output tokens per second
- **Latency Metrics (p50, p95, p99, Mean):**
  - `ttft`: Time to First Token (ms) — prefill duration & queue wait
  - `tpot`: Time per Output Token (ms) — decode token generation speed
  - `itl`: Inter-Token Latency (ms) — token-to-token interval
  - `e2el`: End-to-End Latency (ms) — total request duration
- **Detailed Timings (when `--save-detailed` is enabled):**
  - `start_times`: High-resolution monotonic submission timestamp per request
  - `ttfts`: Array of individual TTFTs per request
  - `itls`: Nested array of every inter-token latency for every token generated
  - `input_lens`: Actual prompt lengths processed
  - `output_lens`: Actual completion lengths generated

### 2. Engine Telemetry (`server.log`)
The timestamped server log records:
- Server initialization, model weights loading, and memory profiling.
- Number of allocated GPU KV cache blocks.
- Real-time iteration lines:
  ```
  Iteration(1420): 2 context requests, 8192 context tokens, 6 generation requests, 6 generation tokens, iteration elapsed time: 4.82 ms, GPU KV cache usage: 34.2%
  ```
- CUDA graph compilation, Triton kernel recompiles, NCCL AllReduce sync events.

### 3. Prometheus Scrapes (`metrics_node0.jsonl`)
Continuous background scrape of vLLM's internal metrics:
- `vllm:num_requests_running`: Currently active sequences on GPU.
- `vllm:num_requests_waiting`: Requests queued waiting for memory.
- `vllm:gpu_cache_usage_factor`: Percentage of KV cache memory used.
- `vllm:iteration_tokens_total`: Tokens processed per iteration.

### 4. Wave, Pause & Stall Analytics (`pause_scan.csv` & `BENCH_SUMMARY_WAVES.txt`)
- `lone_read_s`: Baseline prompt prefill latency with no concurrent load.
- `step_reads`: First-wave prompt spacing.
- `burst_share`: Percentage of total wait time caused by the initial arrival burst.
- `stall_count`: Count of token gaps > 100ms.
- `pause_detected`: Boolean flag indicating whether a decode silence exceeded 3 normal steps.

### 5. Profiling Traces (`.nsys-rep` and Chrome Traces)
- `*.nsys-rep`: NVIDIA Nsight Systems capture with CUDA kernel execution, memory copies, and NCCL communication events.
- `torch_trace_*.json`: Chrome-compatible trace viewable at `chrome://tracing` or Perfetto, displaying CPU op dispatch and CUDA runtime events.
