# V8 gaps and re-run plan — what actually failed, what did not, and what is worth running next

*v1 (4 Oct 2026). Companion to `Master_Dashboard_Review_v1.2`, `Dashboard_Fix_Verification_v1.2` and the magnifying-glass note v1.2. Every statement below was checked against the V8 archive (`combined_vllm_runs.csv`, the per-run `SERVER_COMMAND.txt` and bench JSONs, `NCCL_POLICY_AUDIT.json`, the Nsight per-worker exports, the torch profiles), not against the dashboard or any summary of it.*

**What this note answers.** The team's "what failed in V8 / what to re-run" analysis, row by row and proposal by proposal, followed by the gaps that analysis does not mention and a re-run plan ordered by what each run can change in the published numbers per hour of machine time.

## 0. Verdict in one paragraph

Of the five "failed or missing" rows, two are right (50G/10G serving was never run; the NCCL audit flag is a false alarm), one is half right (the PP4 stage imbalance is structural, but the stage that is heavy and the size of the bubble are both wrong), and two are wrong in ways that would mislead if forwarded: decode profiling did not fail — the decode budget is measured graphs-on and closes on the serving token within 1%, what failed is the multi-node Nsight *export*; and the "0.12% FP8 difference inside the noise floor" cannot exist, because no FP8 KV run ever produced a result. The variance row is also overstated: the archive already contains 2–4 effective repeats of ten operating points and they put the single-request noise floor at ≤ 0.6% and the long-prompt loaded floor at ≤ 0.5%. Of the five proposed re-runs, two are right as stated (graphs-on decode capture; targeted repeats), one is right with two corrections (DP = 2 × TP8, with EP kept inside a node and run under load), one should be redirected (NUMA pinning — the stall it targets was never measured; the CPU-side effect the data does show is the API server under load), and one is premature (long-context accuracy for an FP8 KV cache that does not yet run on this stack). The list misses the five cheapest, highest-leverage runs: the 8K chunk-budget check (5 minutes, could change every loaded 8K first-token number), the distributed layouts under load (the largest coverage hole in V8), the PP2 15/12 split, the 8-GPU KV-pool question, and prompts shorter than 8K, which were never run.

## 2. The five proposed re-runs, assessed

| # | Proposal | Verdict | Why, and what to change |
|---|---|---|---|
| 1 | True decode kernel breakdown, CUDA Graphs on + NVTX | **Yes — as sharpening, ~1 h** | The decode budget is already *measured* graphs-on (torch) and closes within 1%, so this does not "replace an estimate". What Nsight adds is the per-kernel timeline: wave-quantisation tails and launch gaps inside the "kernels above the memory floor" segment, and the cause of the TP8 gap (58.7 µs per AllReduce call in serving vs 37.6 µs in nccl-tests — the socket crossing was ruled out at ≤ 0.4 µs). Capture with `nsys profile --cuda-graph-trace=node` on TP4 and TP8 at c1, c8 and c32 (the batched captures were eager too), and fix the per-worker export before the multi-node captures are repeated. |
| 2 | DP = 2 × TP = 8 (+ expert parallelism) on 16 GPUs at 8K / 128K / 512K | **Yes — with two corrections, ~3 h** | DP = 2 as one TP8 replica per node is sound: no cross-node collective in the forward pass, KV pool 2 × 8.2 M tokens, and every per-replica latency is already known from TP8/PP1 (first token 0.26 s at 8K, 75 s at 1M; token 6.4 / 12.1 ms), so single-request points would only reproduce it. Correction 1: run it **under load** — 8K c8–c64 and open loop, 128K c4–c16, 512K c2–c4 — because the new information is the DP coordinator (lockstep steps, dummy forward passes for idle ranks — vLLM's "waves"), routing fairness between replicas and aggregate usable tokens/s; enable the engine's DP/cudagraph metrics. Correction 2: keep EP **inside a node**. The fabric costs 200–300 µs per small cross-node message (D8); an all-to-all per MoE layer across nodes, 26 layers per step, would add more per token than TP16's AllReduce does today (11–16 ms). |
| 3 | NUMA node / CPU core pinning to remove "PCIe host-to-device reload stalls at 128K" | **Redirect, 30 min** | The premise is not in the data. No host-to-device reload stall was measured at 128K — the stalls there are other requests' prefill chunks (D2: a token above 100 ms is a chunk, 283 ms each at 128K), and the one case that would have exercised host memory (`tp4_native_offload_pressure`) produced no result. The "cross-NUMA socket" explanation of TP8's extra collective cost was ruled out (≤ 0.4 µs per call against a 21 µs gap) and should come off the dashboard. The CPU-side effect the data *does* show is the time outside the engine growing under load — 15 → 232 ms per request at 8K, 0.19 → 1.0 s at 128K c16 — which is the API server tokenising and admitting simultaneous arrivals one after another (the engine's own clocks are exact: its decode time equals the client's within 0.4% on every loaded run). Test `--api-server-count 2 / 4` and engine-core pinning, and measure first token − queue − prefill. |
| 4 | 128K needle-in-a-haystack recall to prove FP8 KV / "compressed KV sharing" causes no degradation | **Premature** | FP8 KV never ran on this stack (row 5). "Compressed KV sharing" is not something V8 tested — prefix caching shares, it does not compress — and the pilot's prompts are random tokens, which cannot test recall. Order of operations: FP8 KV smoke test (does the server start with `--kv-cache-dtype fp8`; 5 min) → the 1M c1 performance point, where the note predicts the decode token 10.2 → 7.9 ms if the attention backend takes it → accuracy on a real long-context set as a separate study with its own harness. |
| 5 | Statistical repeatability, n ≥ 5 at 8K and 128K | **Yes — targeted, ~2 h** | The noise floor is already known where it is small (§4). Spend the repeats where it is not: 8K c8 and c32, open loop 0.75× / 0.90× / 1.0× (the p95 TPOT at the knee decides "usable" tokens/s), 128K c4 and c8, open loop 0.50×. Five consecutive runs each, same server process, warm engine, prefix caching off. Skip 512K and 1M (0.2–0.5% over n = 3–4). |

## 3. What the list misses

Ranked by what the run can change in the published numbers per hour of machine time.

1. **The 8K prompt equals the chunk budget (5–10 min).** Every 8K run uses 8,192-token prompts with `max_num_batched_tokens 8192`. At one request that is one chunk; under load, one decode token in the step forces a second chunk, and that tail chunk waits a full step behind the next prompt's first chunk. The engine's prefill phase doubles (0.207 → 0.418 s at c4 while the queue is 27 ms), and the per-request trace shows it directly (one wave's first tokens: 0.23, 0.65, 0.87, 0.88 s). Re-run 8K c4 and c32 with the budget at 8,448 (or 8,000-token prompts): if the prefill falls back to ~0.21 s, every loaded 8K first-token number in V8 carries a one-flag artefact and the open-loop 8K first tokens should be re-stated. The decode and usable-throughput numbers are unaffected (they rest on p95 TPOT).
2. **Distributed layouts under load (~3 h).** TP4/PP2, TP8/PP2, TP4/PP4 and TP16/PP1 were run at one request only. Every concurrency, stall, admission and Long-Context c2–c4 panel is single-node, and the dashboard still reads as if it generalised. Run TP4/PP4 and TP16 at 128K c2 / c4 / c8 and 1M c2 / c4 (plus 8K c8), native fabric; add TP4/PP2 if time allows. This is the one run that feeds the most panels.
3. **PP2 15/12 layer split (20 min).** The cost model predicts stage-0 idle 10.1 → 3.2% and first token −3.5% on TP4/PP2 and TP8/PP2 at 128K and 512K; it is the independent test of the model and the cheapest latency win in the plan.
4. **The 8-GPU KV pool question (0 min).** D3: the TP8 pool should be ~19% larger than TP4's (same replicated latent per token, half the weights per GPU) and is 1% larger (8.21 vs 8.14 M tokens). The engine logs the KV block count at start-up; one read of the TP4 and TP8 logs says whether memory is being reserved elsewhere.
5. **Prompts shorter than 8K (30 min).** The shortest prompt in V8 is 8,192 tokens, so the interactive short-prompt regime — where the AllReduce share is highest and the chunk artefact above does not apply — is untested. TP4 at 1K and 2K: c1, c8, c32 and one open-loop sweep.
6. **Re-capture the TP16 512K prefill (15 min).** 1 of 12 ranks usable; the TP16 512K and 1M splits on the wall-time pages are modelled from that one rank.
